### 4.3 B1 の容量と、落ちるものと残す順位

今の規則: 完全 snapshot が 1 MiB（1,048,576 byte）を超えたときだけ、64 KiB を超えた分野がすべて要約になる（`reconstruction/src/view-projector/view-projector.ts:35`〜`:37`・`:904`〜`:906`）。
H37 は EEW・地震・津波を要約にしないと決め、11-14 の α は画面へ渡すものを画面が描く分だけにして根から解くと決めた（p3plan:690）。

B1 は次を条文と表に書く。

1. 落ちる順と残す順位: EEW・地震・津波は要約にしない。
   - 残りの 9 分野は、全体が上限を超えたときに分野の予算を超えた分野から要約になる。
   - EEW・地震・津波の分を先に取るので、要約になる分野が今より増えうる。
   - どの分野が何 byte で要約になるかを、災害の日の筋書き（W1・W2・N1〜N3・R2）で数えて表にする。
2. 分野の予算の配り方: 実測で同時最大の土砂 96,460 byte が分野の予算 65,536 を超えた件（進捗ノート §3 の 2026-10-10 朝の C10）と、気象速報の分野が約 34 subject で予算を超える件（同じく C12 の残存リスク (19)。「見積もり約 60」の単位は読めていない、未確認）を、配り直すか要約を受け入れるかで決める。
3. 公開頻度の上限: 内容が変わった step ごとに最大 1 MiB の直列化が走る（台帳 54、`http-sse.ts:167`〜`:168` の公開ごとの直列化 1 回）。
   - 緊急の更新は即時のまま、ほかは間隔を置く上限を決める。
4. 通常合法最大の manifest（E13a）に、U-T の観測の最大、U-E の複数 EventID、他分野との同時最大、運用区分の混在を入れる（spec:2065）。

### 4.4 P4 の測定 manifest（PM）

固定内容: E01 の P4 の母集団（津波の burst・詳細の射影中の 10 本、群 6 の 3 本、EEW と津波の容量縮退の 13 本）、E04、E25、E26 の条件・標本数（各 100 warm-up、1,000 標本×3 run、spec:2077〜:2078）、時計の対応（spec:1141〜:1143）、判定の場所。
判定の場所は manifest で決める。
Pi の Chromium で実 paint の時刻を取れるかは未測定（未確認）で、予備測定で確かめる。
予備測定で証拠が成り立つことを確かめてから凍結する（p3plan:159 と同じ）。
eew-e01 の予備の経路は同じ manifest で 2 度回すと前の state を戻して入力の番号が結べない（バックログ:251）ので、予備の経路を使う前に置き場を新しくする。
EEW の高速化（バックログ:299）は、Pi の Chromium の T4→T6 を測ってから考える。
今の Mac mini の正式測定の衝突の条件の p99 は T4→T6 が 42.0 ms で、大半が描画である（同じ項）。

## 5. 作者裁定

### 5.1 計画の作者裁定（計画の分け方や順が変わる問い）

旧 Q5（カードの型〔spec の語は器〕の割当表・巡回 60 秒）と S6（最終表示端末）は、9 月の配置の数字（通常の型 214px・見出し 48px）で書いた（spec:1447〜:1450、要判断リスト Q5）。
11-12〜11-17 の試作で配置が変わった（左の列 600px・右の列 536px・時計 540×80 の左下、DS）。
試作の「ふだん」の板では、左の列のカードの高さは中身の行で決まっていて、固定の高さの型は無い（canvas の `D1n-fudan.dc.html`: 今日の地震のカードが上 40px、気象の警報のカードが上 456px、時計が上 960px）。
そこで 3 問を今の配置で作り直した。
4 問目は画面の出方を変えないが、バックログが作者の分岐と書いた（バックログ:253）ので理由を添えてここに置く。

**P4-PLAN-D-SCREEN（S6 の作り直し: 検収する画面と、ほかの大きさの画面）**

解決したい問題: 私が夜にノートの Chrome（1280×720）で FlEq の画面を開くと、Pi の 1920×1080 用に決めた並びがどう見えるかが決まっていない。

分かっていること: Pi は labwc・倍率 1.0・1920×1080・100 Hz、モニタは 530×290 mm（下ごしらえ:136〜:146・:315〜:321）。
Pi の Chromium の devicePixelRatio は未測定（Pi の段 1 で読む）。
視聴距離 1.0〜1.5 m は旧 spec の前提で、実測ではない（`docs/specs/display-design-system.md:307`）。
バックログには、旧築の 1280×720 と 960 幅の P4 要件が 3 項ある（バックログ:353・:359・:362）。

場面: 22:40、福岡・佐賀・長崎に大雨特別警報が出ていて、今日の地震が 3 件ある。
私がノートの Chrome（1280×720）で画面を開く。

| 案 | 画面で何が変わるか |
|---|---|
| ★A 1920×1080 の配置だけを作り、ほかの大きさでは同じ配置を全体ごと縮めて収める | ノートでも Pi と同じ並びが 3 分の 2 の大きさで出る（30px の字は 20px になる）。バックログの 3 項は「縮めて同じ配置」で閉じる |
| B 1920×1080 に加え、1366×768・1280×720 の配置を別に宣言して検収する（旧築の受入の大きさ、`docs/specs/standby-layout-redesign.md:645`） | ノートでは 1280×720 用に詰めた並びが出る。配置の宣言値と検収が 3 組になる。バックログの 3 項は生きる |
| C Pi の 1920×1080 だけを保証し、ほかの大きさは崩れても直さない | ノートでは列が画面からはみ出しうる。バックログの 3 項は外す |

推奨の理由: A は配置の宣言値（D04）を 1 組に保ち、どの大きさでも全部のカードに届く。
B は D-AC06（算術の配置）を 3 組で検収する手間が増える。
R52 が決めたのは、Pi の Chromium の長期稼働を P4 の検収に入れることまでである。
E01 の判定の場所は PM の manifest で決める（Pi の Chromium で実 paint の時刻を取れるかは未確認）。

**P4-PLAN-D-CARD-TYPES（Q5-a の作り直し: カードの型と、テロップの段を作るか）**

解決したい問題: 私が居間で通りがかりに画面を見たとき、流れる熱中症の文を読み終える前に次へ替わる。
カードの高さが固定だと、3 府県分の警報が入らずにカードの中でページが替わる。

分かっていること: spec の器は 4 種（通常 214px・見出し 48px・伸縮・テロップ、spec:1447〜:1450）。
手元の DS の写し（版 32 より前）には、214px の型もテロップの段も無い。
調査のカード 5 の推奨は、テロップを流さず止めた文にして、ほかのカードと同じページ送りに載せる案である（調査:827）。
テロップの段を無くして熱中症と竜巻を 48px の見出しに入れる案は、同じカードの「仕組みを消す案」として並べてある（調査:831）。
テロップの段を作らないと、§11.4 の「津波 chip の再放送（クリックでテロップへ）」（spec:2378、互換必須）の前提が消える。
割当の種別（見出しに置くもの: 火山 L2・氾濫警戒・記録的短時間大雨・南海の調査中）は §8.5.2 の表のまま変えない。

場面: 23:10、福岡・佐賀・長崎の大雨特別警報と、今日の地震 3 件と、熱中症警戒アラートが出ている。

| 案 | 画面で何が変わるか |
|---|---|
| ★A 型を「中身の行で高さが決まるカード（上限は列の残り、超えた分はカードの中のページ送り）」と「48px の見出し」の 2 つにする。テロップの段は作らず、熱中症警戒アラートと竜巻注意情報は 48px の見出しに置く | 警報のカードは 3 府県分の行で伸び、熱中症は左の列の 1 行の見出しで止まって出る。津波 chip の再放送は廃止可へ改める裁定が一緒に要る |
| B 4 つの型を残し、通常の型に固定の高さを決める（値は板で決める）。テロップは画面の下に流す | 警報のカードは固定の高さで、2 府県目からカードの中でページが替わる。熱中症は下の帯を流れる |
| C A と同じ 2 つの型に、テロップの段を残す（流すか止めるかと速さは Pi の段 2 で決める） | 警報のカードは伸びる。熱中症は下の帯に出る（流れ方は後で決まる）。津波 chip の再放送は残る |

推奨の理由: A（調査の「仕組みを消す案」）は流れる文を無くし、止める操作をページのドット 1 つにまとめる（WCAG 2.2.2、調査:822〜:831）。
旧築のテロップの同期は台帳 39・40 の欠陥の根で、作らなければ受入が減る。
テロップを残したい事情があれば C を選ぶ。

**P4-PLAN-D-ROTATION（Q5-b: 自動のページ送りの一巡の上限）**

解決したい問題: 左の列が複数ページになった夜、私が 1 分見ていても後ろのページの警報が一度も出ないことがある。

分かっていること: 字 30px 以上・列 600px で、最大件数のときに何ページになるかは数えていない（未確認。C0 の板で数える）。
1 ページの時間は Pi の段 2 で決める。
「自動送りなし」は、マウス無しで読めなければならない事実を全部カードに残す H49 と合わないので選択肢にしない。

場面: 23:10、6 府県の警報で左の列が 3 ページになった。
誰もドットを押していない。

| 案 | 画面で何が変わるか |
|---|---|
| ★A 一巡の上限を 60 秒にする | 60 秒以内に 3 ページとも 1 回は出る。新着が続いても後ろのページが 60 秒を超えて出ないことは無い（D-AC10） |
| B 一巡の上限を 120 秒にする | 1 ページを長く見られるが、後ろのページが出るまで最長 2 分待つ |

推奨の理由: 旧 Q5-b の推奨（spec:2915）と同じで、1 ページ 10 秒なら 6 ページまで入る（調査:830 の計算）。

**P4-PLAN-D-WALK-SCREEN（ペルソナ歩きの演じ手が見る画面）**

ここに置く理由: 画面の出方は変えないが、バックログが作者の分岐と書いた（バックログ:253）。

解決したい問題: 演じ手は、製品の画面に出ない training・test の行と確認の欄を見て、製品が描く容量超過の行を見ない（バックログ:253）。

### 5.3 統合担当の即断候補

作者の裁定を要しない技術的な細部。
A で進め、B を選ぶときだけ作者に諮る。
決めたら作者へ報告する。

- **A 画面の作りに使う道具**: A 依存を足さず、chrome-eew と同じ tsc の build と素の DOM で作る（`reconstruction/` に package.json が無く、svelte・vite・d3-geo は旧築の `display/package.json:22`〜`:28` にだけある。旧築の `display/` は切替で消えるので借りない）。
  B Svelte を入れる（`reconstruction` に依存を足し、版を固定する）。
  GIS 資材の build（mapshaper）は G0 の build の時だけ使い、生成物を hash 付きで commit する。
- **B 描画方式**: A SVG から始める（spec:1674）。
  Pi の段 1 で初回 paint と更新が条件を満たさなければ、Canvas と比べる（N13）。
- **C 気象の警報の区域名**: A G0 の区域名の表を描画の側で引く（wire は Code のまま、snapshot の byte を増やさない）。
  B wire に区域名を載せる。
